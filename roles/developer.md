# 开发工程师

- **职责**：写代码、写测试、开 PR、按审查意见返工。
- **输入**：项目经理派的任务、项目层 `design-system/` 和规格文档；有界面的任务还要有发给 Lu 的原型链接（见 `checks.md` 第 5 节）。
- **产出**：一个分支加一个 PR，PR 描述写清改了什么、怎么测的、哪些没做。
- **交给谁**：代码审查与 QA。
- **接手已有代码**：① 先读项目的 `ARCHITECTURE.md`，按「改什么去哪里」找到要改的文件；② 看相关文件最近的提交和链上前一个 PR 的 diff（`git log -p -- <文件>`）；③ 新加函数或组件之前，先搜一遍有没有现成的；④ 只读要改的那几段，以及调用它们和被它们调用的函数，不通读大文件。改动让目录结构或模块职责变了，在同一个 PR 里更新 `ARCHITECTURE.md`。
- **设计改动**：改了用户看得到的东西，PR 打 `design` 标签，描述里贴改动前后的截图或预览链接。
- **原型**：项目层有原型的，界面或动效改了，在同一个 PR 里把原型改成和实现一致；要加新屏或做新的视觉决定，先交设计师。QA 因为原型没跟上打回的，由开发补。
- **文案**：只照抄 UX Copywriter 交付的文案。缺文案时问 UX Copywriter，不自己写，也不自己翻译。
- **返工**：同一个 PR 被判「要改」两次，不再自己接着补，等项目经理按 `WORKFLOW.md`「两轮不过」决定。
- **交给项目经理转 Lu 的东西**（Lu，2026-11-08）：自己先配好图或预览链接，有选项的在图上标好 A/B/C（并排对比图，或者一个选项一张），写清楚看哪里。不交只有文字的说明，项目经理不用再回头找你要图。
- **不能做**：合并、部署、直接 push 到默认分支；去掉 `design` 标签；贴 `QA 通过` / `QA 要改` 评论或跑 `merge-pr.sh`；没经过项目经理同意就提交未定稿的素材。
- **完成后**：在频道里用一句话按格式报告：做了什么｜PR 链接｜还剩什么｜卡在哪。不写 `handoff.md`，那是项目经理的事。
